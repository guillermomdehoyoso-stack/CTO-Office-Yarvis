# Yarvis Project Context

## Project Identity

Yarvis is an Operational Reality Platform. Its purpose is to transform
fragmented operational information into traceable knowledge and governed,
explainable operational decisions. The Yarvis Reality Graph represents identity,
governance, relationships, operational context, knowledge, decision intelligence,
and execution without allowing an external system to become canonical truth.

## Current Vision

Yarvis is organized around three enduring capabilities:

```text
Operating Memory -> Operating Reasoning -> Operating Execution
```

Memory preserves evidence and knowledge. Reasoning produces governed decision
support. Execution realizes authorized decisions and records observable outcomes.
Human accountability, explicit authority, provenance, and owner-directed
interactions remain mandatory throughout the platform.

## Architectural Authority

The Yarvis Constitution is the highest architectural authority. Lower artifacts
must conform to it. The applicable order is:

1. Constitution and ratified architecture.
2. Interaction Contract baseline and Architectural Decision Trace.
3. Technical Blueprint and ratified review.
4. Ratified component designs and baselines.
5. Implementation Epics and ratified roadmap amendments.
6. Implementation and post-implementation evidence.

Implementation does not redefine architecture. External sources are evidence,
not canonical truth. Context ownership is singular; projections are
non-authoritative; transactions are context-local by default; and Automation,
Mission Control, and integrations act only through governed owner contracts.

## Current Engineering Phase

**Engineering Foundation (E-001), roadmap-consolidation gate.**

The Core Kernel through F-009 Command Dispatch is recorded as implemented.
Engineering Foundation is not formally complete: Query Dispatch, Event and
Notification foundations, identity/authority envelopes, observability,
conformance completion, worker/scheduler, CI, and the Foundation demonstration
remain governed work.

## Repository Principles

- Modular monolith first; technical sharing never transfers domain authority.
- Every business capability has one authoritative owner.
- Contexts collaborate through explicit contracts, not shared assumptions.
- Commands, Queries, Events, and Notifications retain distinct semantics.
- Evidence, provenance, uncertainty, and historical preservation are explicit.
- Human authority is never inferred or replaced by AI or automation.
- Repository documentation overrides remembered chat context.

## Active Epics and Long-Term Roadmap

The active epic is E-001 Engineering Foundation. E-002 Inbox First follows only
after the Foundation demonstration. E-003 Mission Control, E-004 Execution
Engine, and E-005 Netpay Merchant Operations jointly deepen the first operational
Netpay vertical. E-006 Automation, E-007 Knowledge and Intelligence, and E-008
Energy Fotónica Operations follow under explicit ownership and contract rules.
